Overview

backtest.py replays historical K-line data (fetched from moomoo OpenD) through the exact same decision logic used in live/Paper Trading (macd_engine.py / signal_tracker.py / trade_engine.py / risk_manager.py), bar by bar, to check whether a symbol's configured parameter values would actually have been effective against real past price action.

Validating parameters through Paper Trading requires at least two weeks of live operation. A backtest does the same validation in seconds to minutes, against any historical period you choose.

💡
This manual assumes you've already read the main MACD Trader manual. For the meaning of individual parameters (GC duration, take-profit, stop-loss, etc.), see the MACD Trader User Manual. This manual covers only backtest-specific topics: fetching historical data, quota, caching, and replay fidelity.

Relationship to the main app

backtest.py introduces no new trading logic. It loads a symbol's existing configuration from data/symbols.json and imports the exact same Python modules the live bot uses. This is a deliberate design choice to prevent backtest results from silently diverging from what the live bot would actually do.

Usage

The target symbol must already be registered via the Web GUI or in data/symbols.json (its MACD, entry, exit, and risk settings are read from there).

cd macd_trader
python3 backtest.py <SYMBOL> <start-date> <end-date>

# Example
python3 backtest.py US.MU 2026-07-18 2026-07-24

The console prints each simulated BUY/SELL in the same format as live trading, followed by a summary: total closed trades, total PnL, and the output file path.

⚠️
A very wide date range triggers a real OpenD historical-data fetch (consuming quota) the first time. Start with a short window (1–2 weeks) while you get familiar with the tool.

How Historical K-line Quota Works

moomoo/Futu's historical K-line API is gated by a quota system. Per the official documentation:

ItemDetails
AllocationBased on your account's assets and trading activity (the exact numeric limit isn't publicly documented)
Consumption unitPer stock. The same symbol costs 1 unit regardless of date-range length or number of bars (confirmed empirically)
ResetAuto-released 7 days after the day it was consumed (a rolling window, not monthly)
Rate limitMax 60 requests per 30 seconds (applies only to the first page of a paginated request)

Checking quota status

history_loader.py calls get_history_kl_quota() right before an actual OpenD fetch and logs the used/remaining values. On a cache hit, this call is skipped entirely — no quota is consumed.

Local Cache

Historical price data never changes once it's in the past. Yet re-running a backtest every time you tweak a parameter would otherwise re-fetch the same data from OpenD on every run, wasting quota.

history_loader.py fetches from OpenD only the first time, saves the result as a CSV under data/history/, and reads from that local file on any subsequent request for the same symbol + timeframe + date range.

data/history/US_MU_K_1M_2026-07-18_2026-07-24.csv

This cleanly separates "fetching data" (a one-time operation dependent on OpenD) from "tuning parameters and replaying" (unlimited, fully local).

💡
This cache directory is excluded from Git via .gitignore (it's personal research data).

Fidelity Limitations

The backtest is designed to match live behavior as closely as possible, but two gaps are inherent to the approach. We disclose both here.

① Closed-bar-only approximation

Live trading polls OpenD every 5 seconds and tracks peaks/exits against the live price of the still-forming latest bar. Historical data only contains the closed OHLC (open/high/low/close) of each bar — the path the price took within that bar is not recorded.

Think of live trading as watching a video, while the backtest only sees a snapshot once per minute. Peak-drop-based exits may fire a few minutes earlier or later in the backtest than they would have live.

② GC/DC duration across multi-day gaps

Earlier, the golden-cross duration counter kept accumulating across an overnight market closure, producing meaningless values like "GC duration: 1051 minutes." This has since been fixed: a date change between consecutive bars is now treated as a session boundary, and the GC/DC clock restarts at that bar (this fix also benefits any live bot that stays running across midnight).

③ Daily risk counters don't reset across days

max_daily_trades and max_daily_loss_pct counters are not reset at day boundaries, in either live trading or backtesting (a known v1 limitation). A multi-day backtest can hit these caps partway through the period, suppressing further simulated trades for the rest of the range.

Reading Results

The output CSV uses the exact same schema as live trading's trade_logger.py (timestamp, action, symbol, price, quantity, entry_price, pnl_usd, pnl_pct, hold_minutes, exit_reason, gc_duration, daily_trades).

Output goes to logs/backtest_<SYMBOL>_<start>_<end>.csv, kept separate from live trading's logs/trades_<SYMBOL>.csv. This is deliberate: we previously fixed a bug where all symbols' live trades ended up commingled in one file, so backtest output is isolated on purpose to avoid ever repeating that mistake.

💡
As of v1, report.py does not automatically ingest backtest output. If you want an AI review of backtest results too, just paste the CSV content directly into a chat and ask for an evaluation.

Symbol Screening

A pre-check for whether a candidate symbol is well-suited to this MACD strategy, run before adding it to the watchlist. Triggered from the "🔍 銘柄スクリーニング" button in the Web GUI header (internally calls screen.py).

What it does

  1. Runs one full-day backtest using the default configuration (or the symbol's existing config, if already registered)
  2. Classifies each trade's entry time into the manual's 5 standard trading-hour slots (opening rush / best window / lunch lull / afternoon / closing) and aggregates the trend per slot
  3. Actually re-simulates all 15 possible contiguous window combinations derivable from the 5 slot boundaries (not a naive sum of slot totals - recomputed for real every time, to account for path dependency)
  4. Computes a monthly breakdown so you can check whether a promising window is a robust pattern or one lucky month
  5. Generates an HTML report with a "Copy for AI Review" button

Usage

  1. Click "🔍 銘柄スクリーニング" in the Web GUI header
  2. Enter one or more symbol codes (comma- or newline-separated; each runs as an independent, concurrent job)
  3. Set the period (1 week to 1 year before the end date), end date, market, and target position value
  4. Click "スクリーニング開始" (Start Screening). Expect a few minutes per symbol (1 full-day run + 15 window variants = 16 backtests)
  5. Once finished, open the report via "📄 レポートを開く" and use "🤖 AI評価用にコピー" to paste into a chat for evaluation
⚠️
Screening an unregistered symbol consumes 1 unit of historical K-line quota (billed per stock, resets after 7 days - see How Quota Works).
🧪
Screening itself never auto-decides whether to add a symbol. Evaluating the results and making the final call always goes through an AI conversation (copy-paste), for the same reason described in Reading Results: a fixed judgment algorithm can't keep up with an evolving strategy and would need constant maintenance.

Roadmap

The current v1 is scoped to a single core loop: replay one symbol over one date range.

  • Parameter grid search across multiple combinations (candidate for v2)
  • Batch backtesting across multiple symbols
  • Integrating backtest output into report.py

Grid search is powerful, but it's deferred until the core replay engine's fidelity against real live behavior has been validated over more historical data.
