概要

backtest.py は、moomoo OpenD から取得した過去のK線データに対して、 ライブ運用・Paper Tradingと全く同じ判断ロジック（macd_engine.py / signal_tracker.py / trade_engine.py / risk_manager.py）を バー単位で再生し、その銘柄の設定値が実際の値動きに対して有効だったかを検証するツールです。

Paper Tradingでパラメータを検証するには最低2週間の実運用が必要ですが、バックテストなら 過去の期間を指定するだけで、同じ検証を数秒〜数分で行えます。

💡
本マニュアルは MACD Trader 本体の運用マニュアルを前提とします。 GC継続時間・利確ライン・損切りラインなど設定値そのものの意味は MACD Trader 操作マニュアルを参照してください。 本マニュアルでは、バックテスト特有の話題（過去データ取得・クォータ・キャッシュ・再現精度）のみを扱います。

本体との関係

backtest.py は新しいロジックを持たず、data/symbols.jsonに登録済みの 銘柄設定と、ライブ運用が使っているのと同じPythonモジュールをそのまま読み込んで動作します。 これは「バックテストの判断が実運用の判断と食い違う」というズレを防ぐための、意図的な設計判断です。

使い方

対象銘柄は事前にWeb GUIまたはdata/symbols.jsonに登録されている必要があります（MACD・エントリー・エグジット・リスク設定を読み込むため）。

cd macd_trader
python3 backtest.py <銘柄> <開始日> <終了日>

# 例
python3 backtest.py US.MU 2026-07-18 2026-07-24

実行すると、コンソールに各BUY/SELLがライブ運用と同じ書式で表示され、最後に確定取引数・合計損益・出力ファイルパスのサマリーが出ます。

⚠️
日付範囲を広げすぎると、初回のみOpenDへの過去データ取得（クォータ消費）が発生します。まずは1〜2週間程度の短い期間で試すことをお勧めします。

過去K線クォータの仕組み

moomoo/Futuの過去K線取得APIには「クォータ（利用枠）」があり、公式ドキュメントによると以下のルールで運用されています。

項目内容
配布基準口座の資産・取引状況に応じて配布される（具体的な上限値は非公開）
消費単位「銘柄」単位。同じ銘柄なら期間の長さやK線本数に関わらず1消費（実測で確認済み）
リセット消費した日から7日後に自動解放される（月次ではなくローリング方式）
レート制限30秒あたり最大60リクエスト（ページング時は初回のみ適用）

実測結果

US.MU の1週間分（K_1M、1,950本、2ページに分割取得）を実際に取得して検証したところ：

0 / 300
取得前
→
1 / 300
取得後（使用済み/残り）

ページ数や期間の長さに関わらず、消費はちょうど1でした。銘柄単位の課金であることが実測で確認できます。

クォータ状況の確認方法

history_loader.py は、OpenDから実際にデータを取得する直前に get_history_kl_quota() を呼び出し、使用済み・残りをログに出力します（キャッシュヒット時はこの呼び出し自体スキップされ、クォータは消費されません）。

ローカルキャッシュ

過去の株価データは一度取得すれば変わりません。にもかかわらず、パラメータを変えて何度もバックテストを実行するたびにOpenDへ再取得しにいくと、クォータを無駄に消費してしまいます。

そこで history_loader.py は、初回のみOpenDから取得して data/history/ にCSVとして保存し、2回目以降は同じ銘柄・足種・期間の組み合わせであればローカルファイルから読み込みます。

data/history/US_MU_K_1M_2026-07-18_2026-07-24.csv

これにより、「データ取得」はOpenDに依存する1回きりの操作、「パラメータ調整・再生」は何度でもローカルで完結する操作、として明確に分離されます。

💡
このキャッシュディレクトリは .gitignore でGit管理外になっています（個人の調査用データのため）。

精度の制約

バックテストは実運用に忠実であるよう設計していますが、原理的に避けられない差異が2点あります。正直に開示します。

① バー確定時点でのみ判定する近似

ライブ運用はOpenDを5秒ごとにポーリングし、まだ確定していない「形成中の最新バー」のリアルタイム価格でもピーク追跡・エグジット判定を行っています。 一方、過去データは確定済みバーのOHLC（始値・高値・安値・終値）のみが記録されており、バー内の値動きの過程は分かりません。

例えるなら、ライブ運用は動画を見ながら判断しているのに対し、バックテストは1分ごとの写真を見ながら判断しているようなものです。 ピーク下落系のエグジットタイミングが、ライブと数分ずれる可能性があります。

② 複数日にまたがる場合のGC/DC継続時間

以前は、夜間の市場休止をまたいでGC（ゴールデンクロス）継続時間を数え続けてしまい、「GC継続 1051.0分」のような無意味な値が発生する問題がありました。 現在は日付が変わったタイミングを検出し、GC/DC継続時間の起点を自動的にリセットするよう修正済みです（この修正はライブ運用側にも同じ恩恵があります）。

③ 日次リスクカウンターは複数日でリセットされない

max_daily_trades・max_daily_loss_pct の日次カウンターは、ライブ運用・バックテストのいずれも日付が変わってもリセットされません（v1時点の既知の制約）。 複数日にまたがる長期間のバックテストでは、期間の途中でこれらの上限に達し、それ以降の取引が意図せず抑制される場合があります。

結果の見方

出力されるCSVは、ライブ運用の trade_logger.py と全く同じスキーマです （timestamp, action, symbol, price, quantity, entry_price, pnl_usd, pnl_pct, hold_minutes, exit_reason, gc_duration, daily_trades）。

出力先は logs/backtest_<銘柄>_<開始日>_<終了日>.csv で、ライブ運用の logs/trades_<銘柄>.csv とは別ファイルに分離されています。過去に「全銘柄の取引が1つのファイルに混在してしまう」バグを修正した経緯があるため、意図的にファイルを分けて事故を防いでいます。

💡
v1時点では report.py はこのバックテスト結果を自動では読み込みません。バックテスト結果もAI評価にかけたい場合は、CSVの中身をそのままチャットに貼り付けて評価を依頼してください。

銘柄スクリーニング

新しい銘柄を監視対象に追加する前に、その銘柄がこのMACD戦略に向いているかを事前チェックする機能です。 Web GUIのヘッダーにある「🔍 銘柄スクリーニング」ボタンから実行します（screen.py を内部で呼び出します）。

やっていること

  1. デフォルト設定（既に登録済みならその設定）で終日バックテストを1回実行する
  2. 各取引のエントリー時刻を、マニュアルの5つの標準時間帯（オープニングラッシュ・最良時間帯・ランチ閑散・アフタヌーン・クロージング）に分類し、傾向を集計する
  3. 5時間帯の境界から作れる全15通りの連続時間帯の組み合わせを、それぞれ実際にバックテストで再生する（単純な合算ではなく、逐次依存性を考慮して毎回実際に計算し直す）
  4. 月別の内訳も算出し、特定の月に偏った「まぐれ」でないか確認できるようにする
  5. HTMLレポートと「AI評価用にコピー」ボタンを生成する

使い方

  1. Web GUIのヘッダーで「🔍 銘柄スクリーニング」をクリック
  2. 銘柄コードを入力（カンマまたは改行区切りで複数指定可。指定した銘柄はそれぞれ独立したジョブとして並行実行される）
  3. 期間（1週間〜1年前から）・終了日・市場・想定元本を指定
  4. 「スクリーニング開始」をクリック。1銘柄あたり数分かかる（終日1回＋時間帯15パターン＝計16回のバックテスト）
  5. 完了したら「📄 レポートを開く」から結果を確認し、「🤖 AI評価用にコピー」でチャットに貼り付けて評価を依頼する
⚠️
未登録銘柄の場合、過去K線クォータを1消費します。（銘柄単位の課金・7日でリセット。詳細は過去K線クォータの仕組みを参照）
🧪
このスクリーニング自体は「追加すべきか」を自動判定しません。結果の評価と最終判断は、必ずAIとの対話（コピー＆ペースト）を通じて行ってください。理由は結果の見方と同じで、固定の判定ロジックは戦略の変化に追従できず、メンテナンスコストが高くなるためです。

今後の展開

現在のv1は「1銘柄・1期間を1回再生する」というコア機能に絞っています。

  • 複数パラメータの組み合わせを自動で試すグリッドサーチ（v2で検討）
  • 複数銘柄の一括バックテスト
  • バックテスト結果のreport.pyへの統合

グリッドサーチは強力ですが、まずはこのコアの再生ロジックが実運用の判断と正確に一致することを、より多くの実データで検証してから着手する方針です。
